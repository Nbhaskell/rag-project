## Current settings in rag.py
Heading-aware chunking: markdown and Word files are cut at their headings, one chunk per section, and each chunk starts with a label such as "Barks n Woofs: Pricing and Packages > Boarding" (the first `# ` heading is the document title, otherwise the file name is used). Sections longer than CHUNK_SIZE are cut between lines. PDF and txt files have no headings, so each is one section cut between lines. CHUNK_SIZE 800 characters of text per chunk, OVERLAP 100 (only a last resort for text with no line breaks), TOP_K 4 retrieved chunks, Qwen3 thinking is on by default (`RAG_THINK=0` turns it off for speed on a slow machine; see "Answer behavior"). `MODEL_TIMEOUT` (180 s, `RAG_MODEL_TIMEOUT`) limits every Ollama call through the shared `llm` client (silence for that long, or an answer taking that long in total, raises an error): during the 2026-10-21 baseline runs Ollama stalled on single `/api/chat` requests for 36 and 40 minutes (its server log shows the requests and a llama-server error at the same moment; the PC had not slept), so `run_eval.py` retries a failed question 3 times and records a `model_error` instead of waiting. Raise the limit on a slow machine. Supported file types: .pdf, .docx, .txt, .md (Word lock files starting with `~$` are skipped; docx headings and tables are kept). Scanned PDFs have no extractable text. Older .doc files are not supported (save as .docx).

## Answer behavior
The prompt tells the model to answer directly, include every condition, alternative and exception the context gives, and, for yes/no questions the context answers, to start with Yes or No that agrees with the sentence (without this, "Are dogs allowed?" came back as "Yes, dogs are not allowed." in nearly every run). The "Sources:" line is chosen by `sources_to_show(answer, chunks)` in `rag.py`: nothing for a refusal ("I don't know", detected by `gives_no_answer()` using the `DONT_KNOW` phrase list; an answer that merely adds a caveat still gets sources), otherwise the file of the best-matching chunk, plus another file only if its chunk is within `SOURCE_WINDOW` (0.10) of the best chunk's distance and the answer shares at least `SOURCE_MIN_SHARED` (4) meaningful words with it (the "Title > Section" label line is ignored). `answer_stream()` returns the ranked chunks (`source`, `distance`, `text`, `group`), not file names. For a split question each part is its own `group` and is judged against its own best match, and a part's best passage needs only `SOURCE_MIN_SHARED_BEST` (2) shared words. Listing every retrieved file was right only about 1 time in 3; the new rule is right about 9 times in 10 on the daycare questions. The two thresholds were tuned on those questions (several nearby settings did equally well), so re-check them with `run_eval.py` when the documents change a lot. The prompt also tells the model to work out references like "that trail" or "it" from the earlier messages; before that, "How long is that trail?" failed about 1 run in 8 (retrieval was fine, the model took "that trail" literally).

Real-document findings: with the old prompt, yes/no questions the documents don't cover got a confident "No, we do not offer..." and questions with an exception ("expired yesterday", grace period 5 days) or a numeric cutoff ("5 hours" versus "up to 4 hours") got a verdict that ignored it, 10 runs out of 10. The prompt now says to reply "I don't know." when the context doesn't say, to answer from any rule or fact that applies, and to take exceptions, grace periods and numeric limits into account. Prompt wording alone was whack-a-mole (each wording fixed one question and broke another), so the bigger lever is `THINK`, which lets Qwen3 reason before answering. It is on by default (the user chose this). On the desktop PC it costs about 2 to 5 seconds per answer (up to about 19 for tricky ones) and fixes every miss in the test set. The laptop has no GPU and may be much slower: if so, turn it off by setting the environment variable `RAG_THINK=0` before `python chat.py` or `python run_eval.py` (PowerShell: `$env:RAG_THINK = "0"`; CMD: `set RAG_THINK=0`). Check how the laptop feels before assuming it is fine. Lesson from chunking: cleaner chunks exposed that "answer concisely" made the model keep only the first half of a rule ("may return after 2 days, or with a vet's note" became "after 2 days": wrong 8 runs in 20, versus 0 in 20 with the old noisier chunks), so the prompt asks for completeness instead. Always re-run the eval, repeated, after changing chunking or the prompt. Document tip: label facts the model must find ("Address: 123 ..."), since an unlabeled address line was not recognised without thinking.

## Split search
`retrieve()` in `rag.py` does the search. `split_question()` asks the chat model (no thinking, temperature 0, about 0.2 s) whether the question covers more than one thing and, if so, rewrites it as one short question per thing (at most `MAX_PARTS` 4). The original question and each part are then searched separately, `SUB_TOP_K` (2) passages each, and the results merged. Questions about one thing are searched as before (TOP_K 4). Reason: one embedding of "when do you open, and how much is a bath?" lands between the topics and finds only one. The splitter sometimes splits a single-topic question ("spayed or neutered") into near-duplicates, which does no harm because the original is searched too. `RAG_SPLIT=0` turns it off (useful for comparing runs). A split follow-up part lacks the chat history, but the original question is still searched with it.

## Automatic indexing
`sync_docs()` in `rag.py` brings the index up to date and only re-processes what changed; `watch()` runs it at startup and then whenever the docs folder's file sizes or modified times change (checked every `SYNC_INTERVAL` = 5 s), and `chat.py` runs `watch()` in a background thread (`RAG_WATCH=0` turns that off; `python chat.py --no-browser` skips opening the browser).
- Every chunk carries `source` (the file's path inside `docs/`, forward slashes, so two files with the same name in different folders no longer collide) and `file_hash`, a fingerprint of the file's content plus `INDEX_VERSION`, the embedding model, `CHUNK_SIZE` and `OVERLAP`. A file whose fingerprint differs from the index is indexed again, so changing those settings re-indexes everything by itself. **Bump `INDEX_VERSION` in `rag.py` whenever the way files are read or chunked changes** (the code can't detect that).
- An updated file's new chunks are added first and the old ones deleted afterwards, so a question asked mid-update still finds something. A deleted file's chunks are removed. A file that is unreadable or has no text is reported once and not retried until it changes (an emptied file has its old chunks removed; an unreadable one keeps them).
- A changed file is only read once its size and modified time are the same on two consecutive checks (so a file still being saved is not read half-written). Word's `~$` lock files are ignored.
- An index built before fingerprints existed is upgraded on the first sync (every file is re-indexed once). `ingest()` still rebuilds from scratch and gives the same chunks as a sync.
- `python test_indexing.py` tests all of this in a few seconds with a fake embedding function and temporary folders (no Ollama, never touches `docs/` or `chroma_db/`). A live check with the real server also passed: a document added, edited and deleted while the chat ran was picked up within about 10 s each time and the answers followed.

## JSON API (for n8n and other programs)
`chat.py` is a FastAPI app run by uvicorn (`python chat.py` -> `main()`; `rag.py` is unchanged), with typed request and response models (`AskRequest`, `AskResponse`, `Passage`, ...) and an automatic `/docs` page (Swagger UI, loads its assets from a CDN) and `/openapi.json`; both are host-checked like everything else, and the chat window's own addresses stay out of the docs. The old behaviour is kept on purpose, including the ORDER of the checks (Host header, then token, then body size, then content type, then JSON, then validation), so an unauthenticated caller never gets as far as body parsing; the body is read by hand (`read_json()`) for that reason instead of by a FastAPI body parameter, which would parse the JSON before the token check. All errors are JSON `{"error": ...}` (handlers for 404/405 etc. too). `test_api.py` starts the real app under uvicorn on a free port (20 tests, no Ollama). It serves, besides the chat page and its own streaming `POST /ask` (also `POST /`; the page uses `/ask`), `GET /api/status`, `POST /api/ask` (`{"question", "history"?}` -> `{"answer", "sources", "seconds"}`) and `POST /api/reindex` (`{}` or no body = `sync_docs()`, `{"full": true}` = `ingest()`). Helpers in `rag.py`: `answer()` (non-streaming answer) and `index_status()`. Rules: only `127.0.0.1` is bound; the `Host` header must be `localhost`, `127.0.0.1` or `[::1]` (plus `RAG_ALLOWED_HOSTS`), which blocks DNS-rebinding; `/api/ask` needs `Content-Type: application/json` (a plain browser form post gets 415, so a web page can't drive it cross-site); body limit 100 KB, question limit 2000 characters; if `RAG_API_TOKEN` is set every `/api` request needs `Authorization: Bearer <token>` or `X-API-Key` (the chat window's own `POST /ask` is not token-protected, but since the FastAPI move it only takes JSON up to 100 KB, like the API, so a cross-site form post can no longer drive it); errors are JSON with an `error` field. Always call it as `127.0.0.1`, not `localhost`: on Windows `localhost` resolves to IPv6 `::1` first, where nothing listens, and PowerShell waits about 2 s (Node.js handles it fine). In PowerShell use `Invoke-RestMethod`, not `curl.exe` (quote mangling); `curl` examples are for Command Prompt. `python test_api.py` tests all of it in seconds (stubbed answers, fake embedder, temp folders); a live check with the real server and model also passed.

## Citations (section, page, passages)
- Chunks carry `section` (heading path without the title, "" if none) and, for PDFs, `page` (PDFs are chunked one page at a time via `read_pages()`, so no chunk spans pages; markdown/Word/txt have no page). `chunk_sections()` returns `{"text", "section"}`; `chunk_text()` still returns just the texts. `INDEX_VERSION` is 2, so an older index re-indexes itself on the first sync (the chunk text and count are unchanged: still 47 on the daycare docs).
- `retrieve()` results also carry `section` and `page`. `passages(chunks, shown)` turns them into the API/chat shape `{source, section, page, text (no label line), distance, best, listed}`; `answer()` returns `{"answer", "sources", "passages"}` and the chat window's streaming reply ends with a `{"passages": [...]}` line after `{"sources": [...]}`. The chat page shows them as a collapsed "Passages the model read" list built with `textContent` (never HTML; `test_api.py` checks that). A passage whose file is not in the Sources line is dimmed. `listed` is per file, not per passage, so the page does not tag individual passages as cited.
- A strong/weak "match" badge was measured and dropped: for passages other than the best one, being close to the best in distance did not reliably mean containing the answer (only 11% to 60% of "close" passages did, differing between the two question sets).
- `gives_no_answer()` now treats an answer that opens with "I don't know" but then states a figure (a digit in a sentence that is not itself a "don't know") as a partial answer, so it gets sources. This fixed "Why are you closed on Sundays?" (correct answer, no sources) and multi-topic questions where one part is unknown. Checked on 518 saved answers: it flips exactly 6 (all partial answers) and none of the 31 other refusals. It is a rough rule, not a proven one.
- `RAG_DOCS_DIR` and `RAG_DB_DIR` point the program at other folders (used so tests and evals can run on a separate index while a chat server is running on the real one: a running server's folder watcher would otherwise rebuild a changed index back to its own version).
- `test_answers.py` (refusal rule, passages) and the PDF/Word/section tests in `test_indexing.py` use generated PDFs and Word files; PDF and Word chunking has still not been tried on real-world files.

## Thinking loops (the `treats` question)
- Cause (found 2026-10-21 from Ollama's server.log and saved thinking text): "Will you give my dog treats?" has only a conditional answer in the documents ("Treats are only given with owner permission"), while the prompt told the model to begin a yes/no answer with Yes or No. Qwen3 argued in circles ("it's conditional... but the user's question is a direct yes/no..."; one sentence repeated 21 times) and, with no length limit, kept generating: 12,600 tokens when the 180 s timeout fired, and the two largest generations in the log are exactly 163,840 tokens (10 times the 16,384 context, Ollama's own cutoff, about 38 minutes at 71 tokens/s), which were the two long stalls. The question took 142 to 1,369 tokens even when it did not loop (most questions: a few hundred; 99% of all generations under about 1,100).
- Measured on 20 runs of the question each (3,000-token cap): default 4 looped, median 555 tokens, mean 1,137; presence_penalty 1.0: 0 looped, mean 463; repeat_penalty 1.1: 0 looped, mean 284; prompt sentence allowing a condition: 0 looped, mean 215, max 358, every answer "Treats are only given with owner permission." The sampler penalties were not adopted (they discourage repeated tokens, and answers legitimately repeat words and numbers).
- The first prompt sentence tried (V1, a separate "if the answer depends on a condition, state it instead of forcing Yes or No") stopped the loops and passed every check, but made yes/no and edge answers start with Yes or No far less often (24/30 to 14/30 on the 67 questions, 21/36 to 15/36 held-out): ordinary rules such as grace periods count as "conditions". Four wordings compared on the same 66 yes/no and edge answers plus 20 `treats` runs: old prompt 44/66 start with Yes/No, 7/20 treats runs hit the cap; broad sentence 33/66, 0/20; narrow separate sentence 37/66, 0/20; exception built into the Yes/No rule itself 44/66, 2/20 (all answers mentioned the permission, all 62/66 passes). The last one (V3) was adopted: it keeps the Yes/No habit and the cap and fallback handle the rest.
- Fix: the Yes/No rule in the prompt now ends with "The exception is a rule that only gives a condition and does not say whether this case meets it (for example "Treats are only given with owner permission."): then state the condition instead.", and `MAX_ANSWER_TOKENS` (3000, `RAG_MAX_TOKENS`) caps every answer (`num_predict`, thinking included). An answer that ends with `done_reason == "length"` without having said anything is asked again once with thinking off (`answer_stream()`, tested in `test_answers.py`, also checked against the real model with a 60-token cap).

- Final evals with V3 (3 repeats each, same settings as step 3, runs in `eval_runs/published/` as `fix-loop-v3` and `fix-loop-v3-fresh`): answers 67/67 and 55/55, retrieval identical, yes/no and edge answers starting with Yes or No 25/30 and 21/36 (step 3: 24/30 and 21/36), no timeouts or retries, held-out seconds per question 7.3 to 4.3 and slowest question 135 s to 17 s. Two grader wording flaws are known and not yet fixed (`package-refund` forbids "yes"; `puppy-5-months` wants "6 months" but "6-month threshold" is a correct answer); the held-out file is deliberately not edited to fit the model.

## Hardening (public-demo safety; `guard.py`, `chat.py`, `rag.py`)
- `guard.py` (no Ollama, no index, tested alone in `test_guard.py` with a fake clock): `RateLimiter` (sliding window per visitor, a refused try is not counted), `ConcurrencyGate` (leases that expire after `2 * MODEL_TIMEOUT + 60` s, so a place can never be lost for good: a visitor who disconnects before the streaming answer starts would otherwise leak it forever), `DailyCap` (per UTC day, in memory), `client_ip()` (behind `RAG_PROXY_HOPS` proxies the visitor is that many entries from the RIGHT of `X-Forwarded-For`; entries to the left can be forged and are never used), `Guards.from_env()` (`RAG_RATE_PER_MIN` 30, `RAG_DAILY_LIMIT` off, `RAG_MAX_CONCURRENT` 2, `RAG_PROXY_HOPS` 0, `RAG_ALLOW_REINDEX` on; 0 turns a limit off), and the JSON-lines event log (`setup_logging()`, `log_event()`, `visitor_hash()`, `question_text()`). Uvicorn is started with `proxy_headers=False` on purpose: by default it rewrites the client address from `X-Forwarded-For` when the connection comes from 127.0.0.1 (found by a test), which would bypass `RAG_PROXY_HOPS`.
- Order of checks for a question: Host header -> token (`/api` only) -> per-visitor rate limit -> body size -> content type -> JSON -> validation -> a place for the answer (`admit()`: concurrency gate, then the daily cap, releasing the place if the day is used up) -> the answer. `/health` (no token, host-checked) and `/api/status` are not rate limited. The chat window's `/ask` and `/api/ask` share one allowance.
- Errors: `rag.ServiceError(status, code, message)` and `rag.classify_error()` turn anything that goes wrong into a plain message with a code (`index_empty`, `model_unavailable`, `model_missing`, `model_timeout`, `internal`); `chat.py` adds `busy`, `daily_limit`, `rate_limited`, `reindex_disabled`, `bad_token`, `bad_host`, `too_large`, `not_json`, `bad_request`. Every error body is `{"error", "code", "request_id"}`; unexpected errors never put their text in the response (it goes to the log as `detail`; a test checks that a secret in an exception does not leak). `answer_stream()` raises `index_empty` before the model is asked when the index has no chunks. The chat window's addresses reply with lines of JSON, errors included, and the page reads a last line that has no newline (a refused Host).
- Every response has `X-Request-ID` (also in the log and error bodies) plus `X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY`, `Referrer-Policy: no-referrer` (`RequestInfo` middleware, outermost). `GET /health` returns `{"status", "index_ready"}`.
- Log: `logs/events.jsonl` (git-ignored; `RAG_LOG_DIR`, `RAG_LOG=0` off), a new file each UTC day, 14 kept (`RAG_LOG_DAYS`). Events: `answer` (request id, route api/chat, visitor code, question clipped to 500 chars unless `RAG_LOG_QUESTIONS=0`, history length, sources, retrieved passages as source/section/page/distance without text, answer length, `dont_know`, seconds), `answer_failed` (code, error type and the real detail), `http_error` (every refused request except 404: status, code, path, visitor), `reindex`. Never logged: tokens, headers, addresses (visitors are a salted hash, changing on restart unless `RAG_LOG_SALT`), answer or passage text. `python chat.py` calls `setup_logging()`; tests don't, so they write no log unless they ask.
- `RAG_ALLOW_REINDEX=0` makes `/api/reindex` answer 403 `reindex_disabled` (after the token check); a public server should also set `RAG_WATCH=0`.
- Tests: `test_guard.py` (11), `test_api.py` (32; each test server starts with no limits because the limits are module-level state, the limit tests set their own), `test_answers.py` (11).

## Ingest checks
`python rag.py ingest` prints a summary and warnings at the end: files that can't be read or have no text (skipped), and files with unfilled `[bracket]` placeholders from the templates (still indexed). Warnings never stop ingest. Sync and watch print the same warnings, once per file version.

## Chat memory
The last 3 question/answer pairs (`HISTORY_MESSAGES = 6`) are sent to the model. For follow-ups, retrieval searches with the new question and with the previous question plus the new one, and merges the chunks. In the browser, memory lives in the open tab (refresh or restart clears it).

## Testing
`python run_eval.py` runs the questions in `eval_questions.json` (67 questions for the six daycare documents, 12 of them asking about two or three separate topics: facts, yes/no, edge cases that need a rule or a sum, cross-document, unanswerable, follow-ups) against the pipeline and checks retrieval (did the chunks sent to the model contain the fact? `retrieval_contains` can be one phrase or a list that must all be present), the answer (expected words present, "I don't know" for unanswerable ones) and the "Sources:" line (the expected files are the files containing the `retrieval_contains` phrases, or `expected_sources`; `acceptable_sources` lists extra files that may appear without counting as noise). A question with a `known_issue` note is still run and reported as KNOWN but does not fail the run. `--retrieval-only` skips the chat model (fast); `--id <name>` runs selected questions; `--questions <file>` picks another question file (`eval_questions_samples.json` is for the two old sample files: copy them from `samples/` into `docs/` and ingest first). Run `python rag.py ingest` first. Each run is saved to `eval_runs/<date>_<time>_<label>.json` with its settings (models, chunk size, TOP_K, split search, thinking, git commit; `eval_runs/` is not in git except `eval_runs/published/`), and the latest per-question details also go to `eval_results.json` (not in git). `--label NAME` names a run, `--repeat N` runs all questions N times and lists questions that did not pass every time, and `--compare A B` prints two saved runs (labels or file paths) side by side with the settings that differ and the questions whose pass rate changed. `RAG_TOP_K` overrides TOP_K for an experiment. Run it after changing CHUNK_SIZE, TOP_K, the prompt, the models or the documents. Answers vary run to run, so judge a change by repeating a question 10 or more times, not by one run.

The summary also reports how well retrieval ranks the fact (how often it is in the top chunk, its average rank) and how many characters are sent to the model, so chunking changes can be compared.

Latest results on the six daycare documents (desktop PC, heading-aware chunks, 47 chunks, thinking on, split search on): over three full runs, answers 67/67, retrieval 59/59, about 980 characters sent to the model per question, sources line exactly right 63 of 67 (4 to 5 unneeded files, no needed file missing). Before split search (`RAG_SPLIT=0`) retrieval was 53/59: half of the 12 two-topic questions lost one of their facts. Raising TOP_K also fixed that but only at TOP_K 10 (every fact found, 2.5 times the text, worse rank), so splitting was chosen. `eval_questions.json` still supports the `known_issue` tag for questions that are known to fail; none are tagged now. Before heading-aware chunking (16 fixed 800-character chunks): top-ranked 32/47 (average rank 1.43), about 2,520 characters. With thinking off (`RAG_THINK=0`) the old chunks scored 53/55 (the misses: a photo-of-paper-records question answered "I don't know", and "Where is the daycare located?" because the address line has no "Address:" label); thinking off has not been re-measured with the new chunks. Heading-aware chunking has only been tried on the markdown documents here; PDF and Word files use the same code but have not been tested against real files.
